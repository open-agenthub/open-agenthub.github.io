Questions and approvals ​

An agent stops and waits for a person in two situations. It asks a question: a choice or some free text, such as which of two approaches to take. Or it asks for permission to run a tool. This page explains where both appear, who can answer, and how to reduce the interruptions.

Edition: Community · Who: the session owner answers permission requests. A Collaborator on a shared session (Enterprise) can answer questions too, but not permission requests. Members of a linked Telegram group can answer from the chat (see Chat).

Questions from the agent ​

When Claude Code, Codex or OpenCode asks a question with choices, the Workspace shows it in full, with its options:

  • Click an option to answer.
  • An option such as Type something opens a text field: write your answer and send it.
  • A multi-select question ticks options one by one and moves on with its own step button; at the end, Submit answers sends them. OpenCode shows a review of your answers first.
  • If the question cannot be shown as buttons, the Workspace says so, and Open terminal opens the agent's console to answer there.

While a question is open, the session gets a ? marker in the sidebar, with the question as its tooltip, and its status reads Question open. The home page lists it under Needs you, and the session list can be filtered by Question open. The marker disappears when the question is answered or cancelled, at the end of the turn, when the context is cleared and on a restart. A session that has simply finished its turn and waits for your next message shows The agent is waiting for your reply instead, without a marker.

A question in a session you can only view does not count as needing you.

Not every agent asks this way

Cursor emits no question events, so its questions appear only in its terminal and get no marker. The marker was checked with Claude Code and Codex; OpenCode uses the same question events.

Permission requests ​

In an Interactive session, a tool the agent wants to run raises a permission request, shown above the conversation with what the agent wants to do:

ButtonEffect
AllowRuns the tool this once
Allow (don't ask again)Runs it and allows that tool for the rest of the session
Allow everythingTurns on auto approve for the session and answers this request
DenyRefuses the tool; the agent is told and continues

The same request is sent to your linked Telegram, Signal or Slack chat, where you can answer it as well. Whichever answer arrives first counts. A request nobody answers expires after its waiting period. Codex refuses an unanswered request and reports that the tool was blocked; it does not open a second terminal approval menu. Other agents may fall back to a terminal prompt in an Interactive session. In an unattended session the tool is not run.

Where requests are raised depends on the agent:

  • Claude Code, Codex and OpenCode ask AgentHub on every tool call, so switching auto approve on or off takes effect in the running session.
  • Cursor and OpenClaw read the auto-approve setting once at start; changing it needs a restart.
  • OpenClaw has no per-call hook: an interactive OpenClaw session asks in its own terminal only, and its requests do not reach the web app's buttons or the chat.

Codex permissions ​

Codex uses the session container as its execution boundary. Interactive sessions run commands without an additional CLI sandbox, so you do not need to approve running a command "outside the sandbox" in the terminal. Answer tool permission requests in the Workspace with Allow or Deny, or in a linked chat. The session's tool policy still applies, and changing auto approve takes effect while Codex is running.

AgentHub is the approval surface for Codex. Interactive Codex normally waits up to 30 minutes for your answer; an administrator can shorten that runtime window. Unattended sessions retain a four-minute wait. If nobody answers in time, the tool result says so and you can ask the agent to try again.

An unanswered request or an unavailable approval service blocks the tool instead of handing the decision to another terminal menu. Brief service interruptions are retried when checking policy or polling an existing request. If approval still cannot be reached, the tool result explains that it was denied and can be retried. Ask the agent to try again once the service is available. Agent questions with choices still appear as questions; disabling native tool approvals does not answer those for you.

This applies to Community and Enterprise sessions. Permission buttons are for the session owner; a shared-session Collaborator cannot approve tools. After upgrading to a runtime containing this change, restart an existing Codex session so it uses the new permissions settings. Do not switch Codex's native permissions mode to work around an AgentHub denial.

Requests that come from AgentHub itself ​

Two other kinds of request appear in the same place:

  • Network ports: The agent asks to open network port … when the agent wants to accept or make a connection on a port that is closed by default. See Network ports.
  • Secrets: a banner when the agent asks for a secret with secret_request, with a link to the form where you enter the value. See Secrets.

The account email check ​

Claude Code asks before a tool call would send the signed-in account's email address to the network. In an Interactive session without auto approve, that question is shown in the terminal and you decide. In Autonomous sessions and sessions with auto approve on, AgentHub declines it automatically; auto approve is not treated as consent to share the email address. In permission requests relayed to chat, the detected account email is replaced with [account email].

Fewer interruptions ​

  • Use Allow (don't ask again) for tools you approve over and over.
  • For unattended work, give the session an allow list under Advanced in the New session dialog.
  • Turn on auto approve for a container you would hand over anyway.
