Evaluation checklist ​

A checklist for teams evaluating Open AgentHub on their own infrastructure: what to prepare, the steps from a fresh host to a team signing in, how long each step took when we measured it, and the limits you should know before you start. It follows the Install page; nothing here replaces it. To set up an instance for a pilot team, continue with Pilot setup.

The times below were measured in a deliberately slow environment: an emulated virtual machine (4 vCPU, 10 GB RAM, no hardware acceleration), on release 1.20.0 for the install, the team login and the first sign-in, and on 1.19.0 for the first session and task. Treat them as upper bounds. On ordinary hardware with a fast network the quickstart itself takes about a minute.

What can cost time, so you can avoid it:

  • Ingress class. On the quickstart cluster set ingress.className=traefik; the chart's default class is not the one k3s runs, and the hub is then not reachable at its hostname.
  • An identity provider that is not reachable yet. If the backend cannot validate the identity provider, it stops with one clear error and is restarted; helm upgrade --wait waits until it succeeds or its timeout (5 minutes in the documented command) runs out. Make sure the provider answers from inside the cluster first, and check kubectl logs -n agenthub deployment/agenthub-backend early; the previous version keeps serving meanwhile.

The workflow to try ​

A good first evaluation, with two or three colleagues:

  1. The administrator maps identity-provider groups to admin or user, sets a monthly API budget for a group, and limits which agents may be started (Settings → Usage limits & groups). Enterprise.
  2. Create a project and share it with a reviewer as Viewer. Enterprise.
  3. Start an Interactive session from an issue: agent, model, repository and the issue text as the task. Answer the first tool approval; Allow (don't ask again) covers that tool for the rest of the session.
  4. The agent works on a branch and pushes it. Opening the pull request needs a token or OAuth app that allows it on your Git host.
  5. Share the running session with a colleague as Collaborator; they find it under Shared with me and continue the conversation. Enterprise.
  6. Switch the session's model between turns from the model menu in the session bar — see Choosing a model.
  7. Create a read-only link, open it in a private window, and revoke it. Enterprise.
  8. Restrict the session's MCP servers or tools under MCP security in the Share dialog — see Sharing. Enterprise.

Known limits ​

  • Enterprise licence. The checkout under Settings → License asks for payment details. There is no hosted instance to try.
  • Tool approvals belong to the session owner. A collaborator can type into a shared session but cannot answer its approval prompts; the owner answers them, or allows a tool for the whole session.
  • MCP restrictions have limits. Blocking single tools works for Claude, Codex and OpenCode; for Cursor and OpenClaw only whole servers can be blocked. A changed server list applies after the session restarts. The restrictions cover MCP only: they do not block network access or secrets that the agent can reach from its shell.
  • Sessions created with the quickstart API key stay with the user admin after you switch to single sign-on.
  • OpenClaw sessions do not appear in Slack, Telegram or Signal.
  • The first session start is slow because the agent image is pulled on first use.
