Switch agent provider ​

Experimental (1.21.1)

Switching providers is experimental and off by default: it needs persistent session workspaces (agent.workspaceVolume.persistent), which an operator has to enable. Recovery after a crash or a lost pod in the middle of a switch is still being hardened: an interrupted switch is held and the owner can retry or cancel it, and native state is required to resume a completed switch. Keep the option off in production until a later release completes this.

The session owner can replace a Claude agent with Codex, or Codex with Claude, while keeping the same session and visible Workspace conversation. The new agent starts a fresh native conversation on the same workspace volume, including dirty and untracked repository files. Switching back starts another fresh native conversation; it does not resume an earlier agent.

This is a Community feature. Only the owner can review, start, cancel or retry a switch. Enterprise sharing links and roles stay attached to the session. Collaborators and Viewers can continue to read permitted history, but sharing grants no switching authority. Peer agents and parent sessions cannot switch another owner's session through MCP.

Before switching ​

Use a packaged Claude or Codex Interactive session with the Terminal interface, running without root privileges. Its workspace must have been created on a persistent volume. Existing sessions using temporary emptyDir storage show switching not available, with a reason. They are not migrated automatically; create a new persistent-workspace session.

Configure the target provider's usable subscription account or API key first in Provider login. Custom model endpoints need a known, sufficiently large context window. A missing optional context-window value does not block the pinned native default or discovered built-in models: admission uses a conservative 100,000-token minimum. A reported window takes precedence, including a smaller one. Unknown custom capacity is refused.

Finish the current turn, resolve approvals and questions, clear draft input and CLI menus, and close shell terminals and helper containers. Busy or uncertain runtime state is refused. Keep the target account available until the replacement finishes; a rejected login or exhausted account must be fixed before retrying.

Review and start ​

  1. Open Switch provider in the session's Workspace controls.
  2. Select the other provider, its authentication mode and account, and the model settings.
  3. Enter the instructions, current task, decisions, pending work and references the next agent needs. Review the exact framed handover, including its omission note.
  4. Start the reviewed replacement. Editing the selection invalidates the review.

Only the reviewed text becomes the new agent's first native user turn. The complete text, including framing and the request marker, is limited to 16,000 characters. Oversized selections are refused rather than silently shortened. References stay plain text; they do not fetch files or attach their contents. Do not include credentials in the handover.

Earlier native messages, raw tool output, attachments, hidden reasoning and native resume files are omitted from the handover. Visible history is not the target model's context. The new agent can inspect the preserved workspace through its normal permitted tools. Only workspace files persist: processes and memory from the old pod are not transferred. Stop background services before switching and restart needed services in the new runtime.

The source agent checkpoints and exits before its pod is removed. AgentHub waits for all pods using the workspace to disappear, then starts the other provider in a replacement pod. The replacement has a fresh home and only the selected target provider's credentials; source native state is never translated or restored into it. Approval mode, tool restrictions, MCP access, selected session secrets and network policy remain in effect. Old approvals are not carried over as permission for new calls.

During replacement and on failure ​

Workspace input and competing maintenance actions are held while the switch is pending. Fleet messages remain queued until the target handover is committed. Cancelling before source shutdown releases queued messages back to the original agent. The target's initial input cannot be replaced by a queued message.

Cancel is available only before native source shutdown begins. Afterwards, use Retry when the reported problem is fixed. A retry checks the same durable operation and target; it does not retype an uncertain handover or automatically create a second target. If native shutdown, storage, pod identity or delivery cannot be confirmed, the switch stays held with an explanation. There is no automatic rollback to the source agent. Deleting the session also deletes its owned workspace claim, so preserve needed files before choosing deletion.

The session keeps one visible conversation with provider boundaries. Combined history has retention limits and explicit omission notes; see Handover preview. Completed execution usage is shown separately by provider/account where available.

Resume after a completed switch ​

From 1.21.1, resuming a completed switch requires the saved native conversation for its current provider and execution. If that archive is missing or cannot be restored, resume refuses to start. The persistent workspace is retained, and the original task is not submitted again. Runtime maintenance uses the current execution's archive too.

Restore the current archive and retry Resume. A previous provider's archive, an earlier execution of the same provider, or the visible conversation cannot replace the missing native state. If it cannot be recovered, ask your administrator to preserve the workspace before deleting the session: deletion also removes its owned workspace claim.

Operator storage settings ​

Enable persistent workspaces for newly created supported sessions in Helm values:

yaml
agent:
  workspaceVolume:
    persistent: true
    size: 10Gi
    storageClass: ""

An empty storageClass uses the cluster default. Choose a class supporting writable filesystem claims and suitable capacity for each session. Each new supported session gets its own claim; existing temporary workspaces are unchanged. Disabling the flag stops new admission but existing recorded claims still mount on resume and are cleaned up on deletion.

Pause and failed switches retain the claim. Session deletion stops producers and deletes the owned claim before removing its registry record. A storage class with a Retain reclaim policy can leave the underlying volume for operator cleanup and associated storage charges.

A persistent workspace is not a backup. Native state archives contain provider state, not dirty repositories. Back up a quiesced workspace together with consistent session database, execution history and object-storage artifacts. Restoring a missing claim from a native state archive cannot reconstruct the workspace. Volume snapshot automation and migration of old emptyDir sessions are outside this feature.
